# 서브컬처 너머로의 확장과 다중 브랜드

- 상태: 아이디어 (2026-11-02 논의). 확정된 계획이 아니며 로드맵에 올리지 않았다.
- 해당 시점: 한참 뒤. 지금은 서브컬처 행사에 집중한다.

## 배경

행사·공연·이벤트는 구조가 거의 같다(일정, 장소, 주최, 참가자, 굿즈·티켓). 그래서 서브컬처 전용으로 만든 시스템이 일반 행사에도 쓰일 수 있다. 다만 일반 행사 분야에는 이미 큰 서비스가 많아서, 처음부터 넓게 가면 현재 차별점(서브컬처 특화, 글로벌, ICS 캘린더 구독)이 흐려진다.

## 방향

**시스템은 하나로 두고 브랜드를 나눈다.** 서브컬처는 "첫 번째 브랜드"이고, 나중에 다른 분야 브랜드를 추가한다.

- 서브컬처 팬에게는 서브컬처 전용 서비스로, 일반 관객에게는 일반 서비스로 보인다.
- 한 브랜드를 바꾸거나 내려도 다른 브랜드에 영향이 적다.
- 데이터 수집·API·ICS·다국어 같은 핵심 기능은 한 번만 만든다.
- 지금 이름 "Subculture Link Stage"를 바꿀 필요가 없다.

## 구조 초안

"사이트 등록" 구조다.

1. **Onstage는 코드 하나, 배포는 브랜드마다.** 브랜드 이름·로고·색·문구·도메인은 설정값으로 바꾼다.
2. **API에 "사이트" 목록을 둔다.** 사이트마다 도메인, 브랜드 정보, 보여줄 카테고리를 등록한다.
3. **Onstage가 API를 부를 때 자기 사이트를 알린다.** API가 그 사이트에 맞는 데이터만 내려준다.
4. **Backstage에서 사이트를 등록·수정한다.** 행사 데이터는 하나로 관리하고, 각 행사를 어느 사이트에 보여줄지 고른다.

새 브랜드를 만들 때는 사이트를 등록하고 Onstage를 한 번 더 배포하면 되고, 코드를 새로 짤 일은 거의 없다.

## 미리 정해 둘 것 (미정)

- **사이트 구분 방법**: 요청의 도메인(Origin)으로 구분할지, 사이트마다 발급한 키로 구분할지. 키 방식이 더 단순하고 안전해 보인다.
- **행사와 사이트 연결**: 행사마다 직접 고를지, 카테고리 규칙으로 자동 연결할지. 자동 규칙에 직접 예외 지정을 더하는 방식이 후보다.
- **허용 도메인(CORS)**: 사이트를 등록하면 그 도메인의 요청을 API가 허용하도록 한다.
- **사용자 계정**: 브랜드마다 따로 둘지, 한 계정으로 같이 쓸지. 한 계정이 편하지만 브랜드가 섞여 보일 수 있다.
- **운영 부담**: 시스템은 하나여도 홍보·SNS·문의 대응은 브랜드 수만큼 늘어난다. 혼자 시작하는 동안은 가장 큰 부담이다.
- **DB 변경 순서**: 지금은 DB가 하나뿐이라 마이그레이션이 실제 DB에 바로 반영된다. "기본 사이트" 하나를 먼저 만들고 기존 행사를 전부 거기에 연결하는 순서로 가야 기존 데이터가 깨지지 않는다.

## 지금 해 둘 일 (작은 것)

실제 착수 전이라도 아래 두 가지만 지키면 나중에 비용이 크게 줄어든다.

- 화면에서 브랜드 이름·로고·색·문구를 코드에 박지 않고 설정값으로 둔다.
- "서브컬처"를 코드·DB 구조에 하드코딩하지 않고 카테고리·태그·시리즈 같은 일반적인 구조로 둔다.

## 착수 신호

- 서브컬처 안에서 사용자가 어느 정도 쌓였을 때
- 인접 분야(버튜버 콘서트, 게임 행사, 일반 공연 등)를 넣어 달라는 요청이 자주 들어올 때
- 위 신호가 보이면 이 문서를 기획 문서(아키텍처·DB·API)와 로드맵으로 옮긴다.
