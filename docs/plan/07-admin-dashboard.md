# 07. 관리자 대시보드 (Subculture Backstage)

## 7.1 수집 후보 관리

- 미검수 후보 목록
- 신뢰도순·출처순·행사순 정렬
- 원문과 자동 번역 동시 표시
- 과거 승인·거절 유사 문서 표시
- 기존 행사 데이터와 변경 제안 비교
- 원본 링크 및 저장 스냅샷 확인
- 승인·일부 승인·거절·참고 처리

## 7.2 행사 데이터 관리

- 행사 시리즈 CRUD
- 행사 및 개별 일정 CRUD
- 장소, 주최사, 작품/IP, 인물 연결
- 태그 그룹 및 태그 관리
- 공식 URL 및 출처 연결
- 상태 및 변경 이력 확인

## 7.3 수집 소스 관리

- 출처 URL 및 계정 등록
- 수집 방식 설정
- CSS Selector, XPath, JSON Path 등록
- 포함·제외 규칙 등록
- 수집 주기 및 우선순위 설정
- 마지막 성공·실패 시각 확인
- 일시중지 및 재활성화

## 7.4 번역 관리

- 언어별 번역 상태 확인
- 원문과 번역 비교
- 용어집 적용 결과 확인
- OUTDATED 번역 목록
- 번역 수정 요청 처리
- 용어집 제안 처리
- 특정 용어 변경 영향 범위 확인

## 7.5 운영 관리

- Worker Queue 상태
- 수집·분석·번역 실패 작업 재시도
- 스토리지 사용량
- API 요청량
- 알림 발송 성공·실패
- 최근 데이터 변경 감사 로그

## 7.6 인증 및 권한 구조

Onstage와 Backstage는 인증 방식을 완전히 분리한다. 두 시스템의 사용자 성격이 다르기 때문이다 — Onstage는 불특정 다수의 일반 사용자, Backstage는 소수의 신뢰된 내부 운영 인력과 행사 측 담당자([02-users-and-scope.md §2.1.3](02-users-and-scope.md#213-행사-측-담당자-행사-관리자))로 구성된다.

### 7.6.1 Onstage 인증

- Google 등 소셜 로그인 사용
- "사용자 계정 및 개인 구독"은 후기 확장 기능([02-users-and-scope.md §2.2.4](02-users-and-scope.md#224-후기-확장-기능))이므로 Phase 1에는 로그인 자체가 없음
- 도입 시점에도 Backstage 인증 체계와 독립적으로 운영

### 7.6.2 Backstage 인증 — 3단계 구조

**① 루트 관리자 (사이트 운영자)**

- 현재 1인 운영이라 감사 로그의 실효성이 낮음 — 지정된 단일 로그인 방식(소셜 로그인 미사용, 세션 또는 JWT 기반 ID/PW 등)의 계정으로 운영
- ADMIN/DATA_REVIEWER/TRANSLATION_REVIEWER 등 내부 역할 등록·해제 권한을 독점
- 행사 관리자 계정(대표·하위 모두) 최초 등록 권한을 독점
- 운영 인력이 늘어나면 계정 분리 및 개인별 감사 로그 재검토 필요

**② 행사 관리자 대표 (행사별 1인 이상)**

- 로그인 방식은 자유(소셜/이메일 등 무관) — 로그인 수단이 아니라 권한 부여 절차가 보안 경계이므로
- 자기 행사에 속한 하위 계정 조회·제거 가능
- 신규 하위 계정 등록은 불가 — 대표가 임의로 팀을 확장하지 못하도록 의도적으로 제한, 등록은 루트 관리자만 수행

**③ 행사 관리자 하위 계정 (행사별 팀원)**

- 로그인 방식 자유
- 자기 행사 데이터에 한해 수정 제안 가능하나, 공개 DB에 즉시 반영되지 않고 기존 [change_proposals 파이프라인](03-architecture-and-domain.md#35-데이터-계층)을 거쳐 내부 검수 후 반영
- 등록은 루트 관리자만 가능(대표도 등록 불가)

### 7.6.3 권한 부여 절차 (초안)

1. 루트 관리자가 특정 event_id에 연결된 초대 코드/링크 발급
2. 공식 채널로 확인된 행사 측 담당자에게 직접 전달(신원 확인은 이 단계에서 수동 처리)
3. 담당자가 원하는 방식으로 로그인/가입 후 초대 코드를 사용해 해당 event_id 스코프 권한 획득

> **미결 사항**: 신원 확인 절차의 구체적 기준(공식 SNS 계정 DM만 인정할지, 이메일 도메인 검증을 병행할지 등)과, 행사 관리자 대표 지정 기준(최초 등록자를 대표로 고정할지, 루트 관리자가 별도 지정할지)은 아직 정해지지 않았다. 구현 착수 전 확정 필요.

> **결정 (2026-09-01)**: 루트 관리자 세션은 DB 저장 세션 + HttpOnly 쿠키 방식으로 구현했다(JWT 대신 — 1인 운영 규모에서 즉시 무효화가 쉬운 쪽을 택함). `staff_sessions` 테이블에 세션 토큰의 해시만 저장한다. 비밀번호 복구는 별도 셀프서비스 없이, 운영자가 `create-root-admin` 스크립트로 직접 재설정한다(이메일 발송 인프라가 없으므로). 구현: `scls-platform` repo의 `apps/api/src/lib/session.ts`, `apps/api/src/routes/auth.ts`, `apps/api/src/scripts/create-root-admin.ts` 참고.

권한 역할 구분은 [10-infra-ops-security.md §보안 및 권한](10-infra-ops-security.md)의 역할 목록을 따르되, 행사 관리자 관련 권한은 전역 역할이 아니라 event_id 단위로 스코프되는 별도 권한 매핑으로 관리한다.
