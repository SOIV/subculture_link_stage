# 07. 관리자 대시보드 (Subculture Backstage)

> [!NOTE]
> 현재 Private `scls-platform`에서 루트 관리자 로그인, 행사·일정·기준 데이터 수동 관리 UI와 관리자 UI 다국어 지원을 구현했다. 아래에는 향후 수집·검수·번역 및 행사 관리자 기능 설계도 포함한다. 구현 범위와 남은 작업은 [로드맵](11-roadmap-and-success.md)을 참고한다.

## 7.1 수집 후보 관리

- 미검수 후보 목록
- 신뢰도순·출처순·행사순 정렬
- 원문과 자동 번역 동시 표시
- 과거 승인·거절 유사 문서 표시
- 기존 행사 데이터와 변경 제안 비교
- 원본 링크 및 저장 스냅샷 확인
- 승인·일부 승인·거절·참고 처리

## 7.2 행사 데이터 관리

- 행사 시리즈 CRUD
- 행사 및 개별 일정 CRUD
- 장소, 주최사, 작품/IP, 인물 연결
- 태그 그룹 및 태그 관리
- 공식 URL 및 출처 연결
- 상태 및 변경 이력 확인

## 7.3 수집 소스 관리

- 출처 URL 및 계정 등록
- 수집 방식 설정
- CSS Selector, XPath, JSON Path 등록
- 포함·제외 규칙 등록
- 수집 주기 및 우선순위 설정
- 마지막 성공·실패 시각 확인
- 일시중지 및 재활성화

## 7.4 번역 관리

- 언어별 번역 상태 확인
- 원문과 번역 비교
- 용어집 적용 결과 확인
- OUTDATED 번역 목록
- 번역 수정 요청 처리
- 용어집 제안 처리
- 특정 용어 변경 영향 범위 확인

## 7.5 운영 관리

- Worker Queue 상태
- 수집·분석·번역 실패 작업 재시도
- 스토리지 사용량
- API 요청량
- 알림 발송 성공·실패
- 최근 데이터 변경 감사 로그

## 7.6 인증 및 권한 구조

Onstage와 Backstage는 인증 방식을 완전히 분리한다. 두 시스템의 사용자 성격이 다르기 때문이다 — Onstage는 불특정 다수의 일반 사용자, Backstage는 소수의 신뢰된 내부 운영 인력과 행사 측 담당자([02-users-and-scope.md §2.1.3](02-users-and-scope.md#213-행사-측-담당자-행사-관리자))로 구성된다.

### 7.6.1 Onstage 인증

- Google 등 소셜 로그인 사용
- "사용자 계정 및 개인 구독"은 후기 확장 기능([02-users-and-scope.md §2.2.4](02-users-and-scope.md#224-후기-확장-기능))이므로 Phase 1에는 로그인 자체가 없음
- 도입 시점에도 Backstage 인증 체계와 독립적으로 운영

### 7.6.2 Backstage 인증 — 3단계 구조

**① 루트 관리자 (사이트 운영자)**

- 현재 1인 운영이라 감사 로그의 실효성이 낮음 — 소셜 로그인 없이 ID/PW와 DB 저장 세션 + HttpOnly 쿠키 방식의 루트 관리자 계정으로 운영
- ADMIN/DATA_REVIEWER/TRANSLATION_REVIEWER 등 내부 역할 등록·해제 권한을 독점
- 행사 관리자 계정(대표·하위 모두) 최초 등록 권한을 독점
- 운영 인력이 늘어나면 계정 분리 및 개인별 감사 로그 재검토 필요

**② 행사 관리자 대표 (행사별 1인 이상)**

- '대표'는 주체자 중 대표라는 편의상 명칭이다. 여러 회사가 함께 투자·주최하는 행사에서는 각 주체자가 모두 이 등급을 갖는다.
- 로그인 방식은 자유(소셜/이메일 등 무관) — 로그인 수단이 아니라 권한 부여 절차가 보안 경계이므로
- 자기 행사에 속한 하위 계정 조회·제거 가능
- 신규 하위 계정 등록은 불가 — 대표가 임의로 팀을 확장하지 못하도록 의도적으로 제한, 등록은 루트 관리자만 수행

**③ 행사 관리자 하위 계정 (행사별 팀원)**

- 로그인 방식 자유
- 자기 행사 데이터에 한해 수정 제안 가능하나, 공개 DB에 즉시 반영되지 않고 기존 [change_proposals 파이프라인](03-architecture-and-domain.md#35-데이터-계층)을 거쳐 내부 검수 후 반영
- 등록은 루트 관리자만 가능(대표도 등록 불가)

### 7.6.3 권한 부여 절차

**기본 절차 — 담당자 신청 방식**

1. 담당자가 원하는 방식으로 Backstage에 먼저 가입·로그인
2. 행사 **공식 SNS 계정**(공식 사이트에 게시된 X/Instagram 등)으로 루트 관리자에게 DM을 보내 등록을 요청하며, 가입 시 사용한 계정 식별자(이메일·소셜 ID 등)를 함께 전달
3. 루트 관리자가 DM 발신 계정이 실제 공식 계정인지 확인(인증 배지, 공식 사이트에 게시된 링크와의 대조 등)한 뒤 해당 가입 계정에 event_id 스코프 권한을 수동으로 매핑
4. 최초로 신원 확인된 요청자를 해당 행사의 대표로 지정한다. 이후 팀원 추가는 대표를 통한 요청만 받는다.

**보조 절차 — 초대 코드 방식**

행사 측에 확인 가능한 공식 SNS 계정이 없거나, 루트 관리자가 먼저 담당자를 발굴해 컨택하는 경우 등 기본 절차를 적용하기 어려울 때 사용하는 대체 수단.

1. 루트 관리자가 특정 event_id에 연결된 초대 코드/링크 발급
2. 공식 채널로 확인된 행사 측 담당자에게 직접 전달(신원 확인은 이 단계에서 수동 처리)
3. 담당자가 원하는 방식으로 로그인·가입 후 초대 코드를 사용해 해당 event_id 스코프 권한 획득

> **결정 (2026-09-02)**: 신원 확인 절차는 이메일 인프라를 새로 구축하지 않고, 행사 공식 SNS 계정을 통한 DM 확인으로 처리한다(루트 관리자 세션 결정과 마찬가지로, 1인 운영 규모에서 이메일 발송 시스템 구축 비용을 피하는 방향). 행사 관리자 대표는 최초로 신원 확인된 요청자로 고정하며, 별도 지정 절차는 두지 않는다. 초대 코드 방식은 기본 절차를 쓸 수 없는 예외 상황을 위한 보조 수단으로 남겨둔다.

> **결정 (2026-09-01)**: 루트 관리자 세션은 DB 저장 세션 + HttpOnly 쿠키 방식으로 구현했다(JWT 대신 — 1인 운영 규모에서 즉시 무효화가 쉬운 쪽을 택함). `staff_sessions` 테이블에 세션 토큰의 해시만 저장한다. 비밀번호 복구는 별도 셀프서비스 없이, 운영자가 `create-root-admin` 스크립트로 직접 재설정한다(이메일 발송 인프라가 없으므로). 현재 Private `scls-platform`의 API 구현에 반영되었다. 구현 근거는 [로드맵](11-roadmap-and-success.md)에 정리한다.

> **미결 사항 — 행사 관리자 로그인·인증 방식 설계 (2026-09-19)**: 행사 관리자 대표·하위 계정의 로그인 방식은 위에서 "자유(소셜/이메일 등)"로만 정해 두었고 실제 구현은 루트 관리자 ID/PW 세션뿐이다. 행사 측이 실제로 쓰기 불편하지 않도록 구현 착수 전에 설계를 확정하며, 행사 관리자 계정 도입이 Phase 2([로드맵](11-roadmap-and-success.md))이므로 그 구현 전에 정한다. 범위는 Backstage(행사 측 담당자)에 한정하며, Onstage에는 SSO를 지원할 계획이 없다. 아래는 확정이 아니라 현재 검토 중인 방향이다.
>
> **검토 중인 방향**
>
> - **SSO 로그인(권장, 강제 아님)**: 행사 측은 조직 계정(SSO)으로 가입·로그인하는 방식을 권장한다. 다만 SSO 로그인만으로는 그 사람이 어느 행사를 관리하는지 알 수 없으므로, SSO 로그인 자체로는 행사 권한이 생기지 않는다.
> - **메인 행사 연결 — 소셜 연동 자동 인증**: SSO로 로그인한 계정에 한해, 계정 설정에서 소셜 계정을 연동하면 자동 인증 세션이 진행된다. 연동한 계정이 관리자가 사전에 등록했거나 Onstage에 등록된 행사 공식 SNS 계정이면, 그 계정과 연결된 행사 시리즈(메인으로 쓰는 계정 기준)가 자동으로 연결된다. 한 행사가 여러 소셜 계정을 만들어 시리즈를 나눠 운영하는 경우가 있지만 메인 계정은 그대로이므로, 시리즈마다 따로 인증·관리하지 않고 메인 계정 하나로 관련 시리즈를 묶어 처리한다. 시리즈는 데이터로는 그대로 분리해 두고, 인증·권한을 묶는 단위만 계정 기준으로 한다.
> - **대표 권한은 루트 관리자 확인 후 지급**: 자동 인증이 끝나도 대표 권한을 바로 지급하지 않는다. 루트 관리자가 Backstage에 접속했을 때 인증 결과를 한 번 더 확인한 뒤 지급하는 방지턱을 둔다. 하위 계정은 기존대로 루트 관리자만 등록한다(§7.6.2).
> - **추가 행사 연결 — 증명 자료 제출**: 한 조직이 관리하는 행사가 하나뿐이라는 보장이 없으므로, 메인 계정에 묶이지 않은 행사는 별도 목록에서 행사를 찾아 증명 자료와 함께 연결을 요청한다. 루트 관리자가 자료를 보고 승인 또는 거부한다.
> - **공동 주체자는 같은 등급으로 등록**: 여러 회사가 함께 투자해 여는 행사(예: 조직위원회 구성)에서는 각 주체자가 같은 등급이다. 이미 다른 계정이 소셜 연동으로 대표가 된 행사라도, 주체자임을 인정할 만한 자료를 제출하면 같은 주체자(대표급) 등급으로 등록할 수 있다. 인정 여부와 부여 등급은 루트 관리자가 제출한 자료를 보고 정한다.
> - **소셜·일반 로그인(기존 방식 유지)**: SSO를 쓰지 않는 담당자는 소셜 로그인이나 일반 로그인으로 가입한 뒤 관리자에게 별도로 문의하고, 위 §7.6.3의 절차(공식 SNS DM 확인 → 루트 관리자가 event_id 스코프 매핑)로 등록한다. 자동 인증 로직은 이 로그인 경로에 넣지 않는다. 일반 사용자도 같은 로그인을 쓸 수 있어 매 로그인마다 검사 로직이 돌면 부하와 로딩 지연만 늘 수 있기 때문이다.
>
> **현재 스키마와의 차이**: 위 방향을 구현하려면 사전 등록 공식 SNS 계정 목록, 행사 담당자 계정에 연동된 소셜 신원, 행사 연결 요청(자동 인증 결과·증명 자료·승인 상태)을 담을 구조가 필요한데 [schema.sql](database/schema.sql)에는 아직 없다. `event_urls`의 `SNS` 링크는 표시용 URL이고 `sources`의 `X_ACCOUNT`/`INSTAGRAM_ACCOUNT`는 수집 대상이라 인증 기준으로 쓰는 용도가 아니다. `event_organizer_accounts`는 `login_method`/`login_identifier`만 갖고 있어 SSO 로그인 신원은 담을 수 있지만 소셜 연동 신원은 별도 구조가 필요하다. `event_organizer_permissions.granted_by`가 `staff_accounts`를 필수로 참조하므로 루트 관리자가 최종 확인해 권한을 지급하는 흐름과는 맞는다. 반면 이 테이블의 권한 범위는 `event_id` 단위(`events`)라서, 메인 계정 하나로 행사 시리즈(`event_series`)를 묶어 연결하는 방향과는 맞지 않는다. 시리즈에 나중에 추가되는 회차까지 자동으로 포함해야 하므로 권한 범위를 `event_series_id` 단위로도 둘 수 있어야 하고, `events.event_series_id`가 nullable이라 시리즈에 속하지 않는 단독 행사는 `event_id` 단위를 유지해야 한다. 이 경우 위 §7.6.2와 아래 권한 매핑 설명의 "event_id 스코프" 표현도 함께 정리해야 한다.
>
> 설계 때 확인할 사항은 다음과 같다.
>
> - **SSO 지원 범위**: 행사 측이 어떤 조직 계정 체계를 쓰는지 미리 알 수 없으므로, 가능성 있는 가입·로그인 방식을 넓게 지원하는 방향으로 검토한다. 다만 구조는 IdP를 나중에 추가하기 쉽게 만들고, 우선순위는 실제 행사 담당자의 수요를 조사해 정한다(수동 트랙으로 문의가 들어올 때 쓰는 계정 종류를 함께 확인하는 방법이 후보). Google Workspace·Microsoft처럼 조직이 많이 쓰는 방식이 우선 후보이고, SSO는 권장일 뿐 강제가 아니므로 특정 IdP를 지원하지 못해도 그 조직이 수동 트랙으로 들어오는 데는 막힘이 없다. Google·Microsoft 로그인은 개인 계정과 같은 진입점이라, 조직 계정만 SSO로 인정하려면 도메인이나 테넌트를 확인하는 방법이 필요하다.
> - **공식 SNS 계정 목록의 구조**: 매칭 기준은 URL이나 핸들이 아니라 플랫폼이 내려주는 안정적인 계정 ID여야 한다(핸들은 바뀔 수 있다). 계정을 행사 시리즈에 연결하는 방향이며, 한 시리즈에 여러 계정이 있을 때 자동 인증에 쓰는 메인 계정과 보조 계정을 어떻게 구분할지, 목록을 누가 어떤 기준으로 등록하는지 정한다.
> - **연동 해제와 권한 회수**: 소셜 연동을 해제하거나 계정이 바뀌었을 때 이미 지급한 권한을 어떻게 다룰지 정한다.
> - **추가 행사 요청 처리**: 증명 자료의 종류와 저장(비공개 스토리지)·보존 기간, 승인·거부 사유 기록, 거부 후 재신청 규칙을 정한다. 등급은 주체자(대표급)와 하위 두 단계라서 스키마의 역할 두 단계와 그대로 대응하지만, 역할 이름은 `EVENT_ORGANIZER_REP`/`EVENT_ORGANIZER` 대신 주체자(대표급)를 `EVENT_OWNER`, 하위를 `EVENT_MEMBER`로 바꾸는 방향으로 한다. 하위 계정을 뜻하는 `EVENT_ORGANIZER`가 "주체자"로 읽히고, 공개 데이터의 `organizers`/`event_organizers`(주최사)와도 이름이 겹치기 때문이다. 기존 문자열의 뜻을 바꿔 재사용하면 이미 있는 값이 조용히 다른 권한이 되므로 새 이름을 쓴다. [04-database-design.md](04-database-design.md), [10-infra-ops-security.md](10-infra-ops-security.md)의 권한 역할 목록, [schema.sql](database/schema.sql)에 남아 있는 기존 이름은 이 설계에 따른 스키마 개정 때 함께 바꾼다. 대표를 "최초로 신원 확인된 요청자로 고정"한다는 위 결정(2026-09-02)은 별도 지정 절차를 두지 않는다는 뜻이므로, 이후 추가되는 주체자는 증명 자료 심사로 등록하는 확장 규칙으로 정리한다.
> - **화면 표시 이름**: 스키마의 역할 이름은 권한 등급을 나타내는 내부 값이고 Onstage나 UI에 보이는 이름과는 별개다. 표시는 계정의 성격에 따라 정한다. 대표 계정이 위원회 측 계정이면 위원회 계정으로, 위원회 없이 회사들만 있으면 각 회사가 주체자로 표시한다. 공개 화면의 주최사 표시가 기존 `organizers`/`event_organizers` 데이터와 어떻게 연결되는지도 함께 정리한다.
> - **결과 통지**: 이메일 발송 인프라가 없어(위 결정 참고) 대표 권한 확인 대기와 승인·거부 결과를 어떻게 알릴지 정한다. 루트 관리자에게는 Backstage 접속 시 확인 대기 목록, 담당자에게는 Backstage 안의 상태 표시가 후보다.
> - **플랫폼별 연동 조건**: 소셜 계정 연동에 쓸 수 있는 OAuth 제공 여부, 비용, 약관은 플랫폼(X, Instagram 등)마다 다르므로 착수 전에 확인한다. 자동 인증을 지원하는 플랫폼과 증명 자료 제출로만 처리하는 플랫폼이 갈릴 수 있다.
> - **콜백 위치**: SSO와 소셜 연동의 OAuth 콜백 URL은 Backstage↔API를 프록시로 동일 오리진에 두기로 한 결정([10 §10.1.2](10-infra-ops-security.md#1012-배포-구조-예시))에 따라 `backstage.*` 아래에 둔다.
> - **구현 방식**: 직접 구현할지 인증 라이브러리를 쓸지는 Private `scls-platform`에서 평가한다.

권한 역할 구분은 [10-infra-ops-security.md §보안 및 권한](10-infra-ops-security.md)의 역할 목록을 따르되, 행사 관리자 관련 권한은 전역 역할이 아니라 event_id 단위로 스코프되는 별도 권한 매핑으로 관리한다.

## 7.7 관리자 UI 다국어 지원

Backstage 관리자 화면 자체의 표시 언어(라벨·버튼·테이블 헤더 등)를 다국어로 지원한다. 이는 행사 콘텐츠(제목·요약 등)의 다국어 저장 구조인 `entity_localizations`([04-database-design.md](04-database-design.md), [06-i18n-translation-glossary.md](06-i18n-translation-glossary.md))와는 완전히 별개의 개념이다 — 전자는 "관리자가 보는 화면 자체의 언어", 후자는 "관리자가 입력하는 행사 데이터의 언어"다.

> **결정 (2026-09-05)**: Backstage는 한국어·영어·일본어 3개 언어를 지원한다. 현재는 운영자 1인만 사용하지만, 향후 [7.6.2](#762-backstage-인증--3단계-구조)의 행사 관리자(대표·하위 계정)가 해외(특히 일본) 행사 담당자로 유입될 가능성이 있어 미리 기반을 잡아둔다. `i18next` + `react-i18next` 기반으로 구현했고, 사이트명("SCLS Backstage")만 언어와 무관하게 고정한다. 언어 선택은 헤더의 드롭다운으로 전환하며 `localStorage`에 저장돼 재방문 시 유지된다. 현재 Private `scls-platform`의 Backstage 구현에 반영되었다.
