# 07. 관리자 대시보드 (Subculture Backstage)

> [!NOTE]
> 현재 Private `scls-platform`에서 루트 관리자 로그인, 행사·일정·기준 데이터 수동 관리 UI와 관리자 UI 다국어 지원을 구현했다. 아래에는 향후 수집·검수·번역 및 행사 관리자 기능 설계도 포함한다. 구현 범위와 남은 작업은 [로드맵](11-roadmap-and-success.md)을 참고한다.

## 7.1 수집 후보 관리

- 미검수 후보 목록
- 신뢰도순·출처순·행사순 정렬
- 원문과 자동 번역 동시 표시
- 과거 승인·거절 유사 문서 표시
- 기존 행사 데이터와 변경 제안 비교
- 원본 링크 및 저장 스냅샷 확인
- 승인·일부 승인·거절·참고 처리

## 7.2 행사 데이터 관리

- 행사 시리즈 CRUD
- 행사 및 개별 일정 CRUD
- 장소, 주최사, 작품/IP, 인물 연결
- 태그 그룹 및 태그 관리
- 공식 URL 및 출처 연결
- 상태 및 변경 이력 확인

## 7.3 수집 소스 관리

- 출처 URL 및 계정 등록
- 수집 방식 설정
- CSS Selector, XPath, JSON Path 등록
- 포함·제외 규칙 등록
- 수집 주기 및 우선순위 설정
- 마지막 성공·실패 시각 확인
- 일시중지 및 재활성화

## 7.4 번역 관리

- 언어별 번역 상태 확인
- 원문과 번역 비교
- 용어집 적용 결과 확인
- OUTDATED 번역 목록
- 번역 수정 요청 처리
- 용어집 제안 처리
- 특정 용어 변경 영향 범위 확인

## 7.5 운영 관리

- Worker Queue 상태
- 수집·분석·번역 실패 작업 재시도
- 스토리지 사용량
- API 요청량
- 알림 발송 성공·실패
- 최근 데이터 변경 감사 로그

## 7.6 인증 및 권한 구조

Onstage와 Backstage는 인증 방식을 완전히 분리한다. 두 시스템의 사용자 성격이 다르기 때문이다 — Onstage는 불특정 다수의 일반 사용자, Backstage는 소수의 신뢰된 내부 운영 인력과 행사 측 담당자([02-users-and-scope.md §2.1.3](02-users-and-scope.md#213-행사-측-담당자-행사-관리자))로 구성된다.

### 7.6.1 Onstage 인증

- Google 등 소셜 로그인 사용
- "사용자 계정 및 개인 구독"은 후기 확장 기능([02-users-and-scope.md §2.2.4](02-users-and-scope.md#224-후기-확장-기능))이므로 Phase 1에는 로그인 자체가 없음
- 도입 시점에도 Backstage 인증 체계와 독립적으로 운영

### 7.6.2 Backstage 인증 — 3단계 구조

**① 루트 관리자 (사이트 운영자)**

- 현재 1인 운영이라 감사 로그의 실효성이 낮음 — 소셜 로그인 없이 ID/PW와 DB 저장 세션 + HttpOnly 쿠키 방식의 루트 관리자 계정으로 운영
- ADMIN/DATA_REVIEWER/TRANSLATION_REVIEWER 등 내부 역할 등록·해제 권한을 독점
- 행사 관리자 계정(대표·하위 모두) 최초 등록 권한을 독점
- 운영 인력이 늘어나면 계정 분리 및 개인별 감사 로그 재검토 필요

**② 행사 관리자 대표 (행사별 1인 이상)**

- '대표'는 주체자 중 대표라는 편의상 명칭이다. 여러 회사가 함께 투자·주최하는 행사에서는 각 주체자가 모두 이 등급을 갖는다.
- 로그인 방식은 자유(소셜/이메일 등 무관) — 로그인 수단이 아니라 권한 부여 절차가 보안 경계이므로
- 자기 행사에 속한 하위 계정 조회·제거 가능
- 신규 하위 계정 등록은 불가 — 대표가 임의로 팀을 확장하지 못하도록 의도적으로 제한, 등록은 루트 관리자만 수행

**③ 행사 관리자 하위 계정 (행사별 팀원)**

- 로그인 방식 자유
- 자기 행사 데이터에 한해 수정 제안 가능하나, 공개 DB에 즉시 반영되지 않고 기존 [change_proposals 파이프라인](03-architecture-and-domain.md#35-데이터-계층)을 거쳐 내부 검수 후 반영
- 등록은 루트 관리자만 가능(대표도 등록 불가)

### 7.6.3 권한 부여 절차

**기본 절차 — 담당자 신청 방식**

1. 담당자가 원하는 방식으로 Backstage에 먼저 가입·로그인
2. 행사 **공식 SNS 계정**(공식 사이트에 게시된 X/Instagram 등)으로 루트 관리자에게 DM을 보내 등록을 요청하며, 가입 시 사용한 계정 식별자(이메일·소셜 ID 등)를 함께 전달
3. 루트 관리자가 DM 발신 계정이 실제 공식 계정인지 확인(인증 배지, 공식 사이트에 게시된 링크와의 대조 등)한 뒤 해당 가입 계정에 event_id 스코프 권한을 수동으로 매핑
4. 최초로 신원 확인된 요청자를 해당 행사의 대표로 지정한다. 이후 팀원 추가는 대표를 통한 요청만 받는다.

**보조 절차 — 초대 코드 방식**

행사 측에 확인 가능한 공식 SNS 계정이 없거나, 루트 관리자가 먼저 담당자를 발굴해 컨택하는 경우 등 기본 절차를 적용하기 어려울 때 사용하는 대체 수단.

1. 루트 관리자가 특정 event_id에 연결된 초대 코드/링크 발급
2. 공식 채널로 확인된 행사 측 담당자에게 직접 전달(신원 확인은 이 단계에서 수동 처리)
3. 담당자가 원하는 방식으로 로그인·가입 후 초대 코드를 사용해 해당 event_id 스코프 권한 획득

**현재 루트 관리자 구현**

- DB 저장 세션 + HttpOnly 쿠키를 사용하며, `staff_sessions`에는 세션 토큰의 해시만 저장한다.
- 비밀번호 재설정은 운영자가 `create-root-admin` 스크립트로 수행한다. 별도 셀프서비스·이메일 발송 인프라는 두지 않는다.
- 행사 담당자 신원 확인의 기본 절차는 공식 SNS DM이며, 초대 코드는 기본 절차를 적용하기 어려울 때만 사용한다.

세션·신원 확인 방식을 선택한 과정은 [인증·인프라 결정 기록](../devlog/auth-and-infrastructure-history.md)에 보관한다.

**미결 — Phase 2 행사 관리자 로그인·인증 설계**

현재 구현은 루트 관리자 ID/PW 세션뿐이다. 아래는 Backstage 행사 담당자 계정을 위한 검토안으로, 계정 도입 전에 확정한다. Onstage에는 SSO를 도입할 계획이 없다. 논의 과정과 세부 검토 근거는 [행사 관리자 인증 검토 기록](../devlog/future-feature-discussions.md)에 보관한다.

| 검토 항목 | 현재 방향 |
|---|---|
| 가입·로그인 | SSO는 권장하되 강제하지 않는다. 소셜·일반 로그인은 기존 수동 권한 부여 절차를 유지한다. |
| 메인 행사 연결 | SSO 계정의 소셜 연동 신원을 공식 SNS 계정과 대조하여 관련 행사 시리즈를 연결하는 안을 검토한다. 자동 인증만으로 권한을 지급하지 않는다. |
| 최종 권한 지급 | 루트 관리자가 인증 결과를 확인한다. 하위 계정 등록도 루트 관리자만 수행한다. |
| 추가 행사·공동 주체자 | 메인 계정에 묶이지 않은 행사나 추가 주체자는 증명 자료를 심사하여 연결·등급을 결정한다. |
| 권한 범위 | 시리즈의 후속 회차까지 포함할 `event_series_id` 범위와 시리즈가 없는 단독 행사의 `event_id` 범위를 함께 설계한다. |
| 역할 이름 | 주체자(대표급)는 `EVENT_OWNER`, 하위는 `EVENT_MEMBER`로 바꾸는 안이다. 기존 역할 문자열을 다른 의미로 재사용하지 않으며, 현재 스키마의 이름은 아직 변경하지 않는다. |
| 콜백 | SSO·소셜 연동 콜백은 `backstage.*` 아래에 둔다 ([§10.1.2](10-infra-ops-security.md#1012-배포-구조-예시)). |

설계 확정 전에 다음 항목을 확인한다.

- 실제 수요에 따른 IdP 우선순위와 조직 도메인·테넌트 검증 방식
- 핸들이 아닌 플랫폼의 안정적인 계정 ID로 관리하는 공식 SNS 목록, 메인·보조 계정 구분과 등록 기준
- 소셜 연동 신원·행사 연결 요청·승인 상태를 저장할 새 구조; 표시용 `event_urls`·수집용 `sources`와 분리
- 연동 해제·계정 변경 시 권한 회수, 증명 자료의 비공개 저장·보존 기간·재신청 규칙
- 주체자·하위 역할 이름과 시리즈 권한에 맞춘 DB·권한 문서 개정, 공개 주최 데이터와 화면 표시 이름의 연결
- 이메일 없이 확인 대기·승인·거부 결과를 알리는 Backstage 상태 표시와 대기 목록
- X·Instagram 등 플랫폼별 OAuth 제공·비용·약관, 수동 심사가 필요한 플랫폼 구분
- Private `scls-platform`에서 직접 구현·인증 라이브러리 사용 여부 평가

권한 역할 구분은 [10-infra-ops-security.md §보안 및 권한](10-infra-ops-security.md)의 역할 목록을 따르되, 행사 관리자 관련 권한은 전역 역할이 아니라 event_id 단위로 스코프되는 별도 권한 매핑으로 관리한다.

## 7.7 관리자 UI 다국어 지원

Backstage 관리자 화면 자체의 표시 언어(라벨·버튼·테이블 헤더 등)를 다국어로 지원한다. 이는 행사 콘텐츠(제목·요약 등)의 다국어 저장 구조인 `entity_localizations`([04-database-design.md](04-database-design.md), [06-i18n-translation-glossary.md](06-i18n-translation-glossary.md))와는 완전히 별개의 개념이다 — 전자는 "관리자가 보는 화면 자체의 언어", 후자는 "관리자가 입력하는 행사 데이터의 언어"다.

현재 Backstage UI는 `i18next` + `react-i18next`로 한국어·영어·일본어를 지원한다. 사이트명 “SCLS Backstage”는 고정하고, 헤더 언어 선택은 `localStorage`에 저장하여 재방문 시 유지한다. 도입 배경은 [인증·관리자 UI 기록](../devlog/auth-and-infrastructure-history.md)에 보관한다.
