# 2026-10 작업 로그

## 2026-10-21 — 수집 출처(Sources) 관리 구현

- 단계·성격: Phase 2 / 구현. Private `scls-platform`의 `main`에 로컬 커밋만 했고, push와 DB migration 적용은 하지 않은 상태의 기록이다.
- 변경:
  - `sources` 표를 추가했다. 설계 DDL([schema.sql](../plan/database/schema.sql))의 칸만 넣었고 `source_rules`·`collection_jobs`는 이번 범위가 아니다. 나중에 `sources.id`를 참조해 붙을 수 있다. 값 목록(출처 유형 9종, 수집 방식 4종)은 기존 방식대로 TEXT + CHECK다.
  - 관리자 API `/admin/sources`: 목록(시리즈·출처 유형·활성 여부 필터)·조회·생성·수정·삭제.
  - Backstage "수집 출처" 화면: 목록 필터, 우선순위·유형·수집 방식·URL·연결 시리즈 표시, 생성·수정 팝업, 삭제, 활성 토글. `terms_note`는 여러 줄 입력이고 비어 있으면 목록에 "미기재"로 표시한다. `last_checked_at`·`last_success_at`은 수집기가 쓰는 값이라 목록에서 읽기만 한다. ko/en/ja 문자열과 메뉴 항목을 함께 넣었다.
  - 초기 9개 시리즈의 출처 32건(공식 사이트 공지·일정 페이지와 공식 SNS 계정)의 입력 데이터와 입력 스크립트(`seed:sources`). 기존 시드 스크립트처럼 미리보기가 기본이고 `--apply`를 붙여야 쓰며, 같은 시리즈에 같은 URL이 있으면 건너뛴다.
- 이유(구현에서 정한 것):
  - 선택 칸(`terms_note`·계정 식별자·수집 주기·시리즈 연결)은 PATCH에서 null을 보내 지울 수 있다. 한 번 적은 이용 조건 메모나 시리즈 연결을 되돌릴 수 있어야 해서 티켓 API와 같은 방식을 썼다.
  - `source_url`은 http(s) 주소만 받는다. 수집기가 가져갈 주소이고 화면에서 링크로 보여 주기 때문이다.
  - `terms_note`가 공백뿐이면 null로 저장한다. "비어 있음"을 한 가지 값으로만 다뤄 목록의 "미기재" 표시가 정확하도록 했다.
  - `event_series_id`는 DDL처럼 삭제 동작을 따로 두지 않아(RESTRICT) 출처가 연결된 시리즈는 지울 수 없다. 행사(`events`)는 Prisma 기본값(SET NULL)이라 다르다. 출처가 시리즈에서 조용히 떨어져 나가 수집기가 시리즈 없는 출처를 가져가는 일을 막으려는 선택이다.
  - `priority`는 큰 값을 목록 위에 보여 준다. 설계 문서에 방향이 없어 가정한 것이며 폼에 안내 문구를 넣었다.
  - 시드 데이터는 모두 비활성이다. 이 조사는 수집 방식의 결정이 아니고, 켜 두면 수집기가 생긴 뒤 지스타(robots.txt가 공지 게시판을 막음)나 Instagram(약관이 자동 수집을 금지)까지 곧바로 가져갈 수 있다. 수집 방식은 조사의 구분을 따랐다 — 정적 HTML 후보(코미케·AGF·PlayX4·코믹월드)만 `HTML_SCRAPE`, X와 YouTube는 `API`, Instagram과 자동 수집 보류·확인 필요 출처는 `MANUAL`. `terms_note`에는 조사 내용만 적고 조사하지 못한 항목(수집 주기 등)은 비워 두었다.
- 관련: [05. 수집 소스 §5.2.1](../plan/05-storage-and-collection.md#521-행사별-수집-프로필), [07. 관리자 대시보드 §7.3](../plan/07-admin-dashboard.md#73-수집-소스-관리), 같은 날짜의 아래 조사 기록. Private `scls-platform` 경로: `packages/db/prisma/schema.prisma`, `packages/db/prisma/migrations/20261021090000_add_sources/`, `apps/api/src/routes/sources.ts`, `apps/api/src/lib/source-input.ts`, `apps/api/src/scripts/seed-sources.ts`, `apps/api/src/scripts/seed-data/sources-2026.ts`, `apps/backstage/src/routes/SourcesPage.tsx`.
- 확인:
  - 실행함: `prisma validate`·`generate`(더미 접속 정보로 실행해 DB에는 접속하지 않음), 타입체크, 린트, 테스트 188건 통과(이 중 Sources 관련 48건 — API 40건, 시드 데이터 검증 8건), 빌드.
  - 화면은 DB 없는 가짜 API로 확인했다(입력 검증은 실제 코드). 필터 4종·생성·수정·삭제·활성 토글·저장 오류 표시·ko/en/ja 문자열은 확인했고, 화면 모드는 다크만 확인했다.
  - 미확인: migration SQL을 실제 PostgreSQL에서 실행, 실제 API·DB와 연결한 화면, `seed:sources` 실행(DB를 읽는 스크립트라 실행하지 않았다).
- 후속: migration 적용(`pnpm --filter @scls/db migrate:deploy`)과 초기 출처 입력은 [로드맵 Phase 2](../plan/11-roadmap-and-success.md)의 "Sources migration 적용·초기 9개 시리즈 출처 입력"에서 관리한다. `priority` 방향은 수집기가 쓰기 시작할 때 확정한다. 출처가 연결된 시리즈를 지우면 API가 400(`INVALID_REFERENCE`)으로 거절하는데 화면은 삭제 확인 문구로만 미리 알리고 실패 안내는 띄우지 않는다(다른 삭제 실패와 같다).

## 2026-10-21 — 초기 9개 시리즈 공식 출처와 SNS API 이용 조건 조사

- 단계·성격: Phase 2 사전 확인 / 검토 중. 조사 결과이며 수집 방식의 결정은 아니다.
- 방법: 2026-10-21에 각 공식 사이트의 첫 화면과 `robots.txt`를 직접 열람하고, SNS API는 공식 개발자 문서를 열람했다. 직접 열람하지 못한 약관은 아래 [미확인](#미확인과-후속)에 구분했다. 사이트 구조는 이 시점 기준이며 회차마다 바뀔 수 있다.
- 관련: [05. 수집 소스](../plan/05-storage-and-collection.md#521-행사별-수집-프로필)의 SNS 수집 리스크 메모, [로드맵 Phase 0](../plan/11-roadmap-and-success.md) "초기 수집 출처·이용 조건 확인"

### 2. 수집 방식 판단

아래는 조사 결과에서 끌어낸 해석이다.

| 구분 | 시리즈 | 근거 |
|---|---|---|
| 정적 HTML 수집 후보 | 코미케, AGF, PlayX4, 코믹월드 | robots.txt가 공지·일정 경로를 막지 않고, 서버 렌더링 HTML과 `sitemap.xml`이 있거나 경로 규칙이 단순하다 |

### 3. SNS API 이용 조건

**X (직접 열람: [이용약관](https://x.com/en/tos)(2026-10-09 시행), [개발자 정책](https://docs.x.com/developer-terms/policy), 개발자 문서 가격 페이지)**
- 가격 체계는 선불 크레딧 방식(pay-per-usage)만 안내된다. 구독 요금제와 무료 등급은 가격 페이지에 나오지 않는다. 월 게시물 읽기 상한은 300만 건이다. 개발자 정책은 아직 Free·Basic·Pro 요금제를 전제로 쓰여 있어 두 문서의 표현이 다르다.
- 읽기 단가는 게시물 $0.005, 사용자 $0.010 (리소스 1건당). 가격은 바뀔 수 있고 Developer Console이 기준이다.
- 추정 비용: 9개 공식 계정에서 하루 게시물 20건을 한 달간 모두 읽으면 5,400건, 약 $27이다. 새 게시물만 증분 조회하면 이보다 훨씬 적다.
- 이용약관은 X가 제공하는 공식 인터페이스 외의 방법(자동화 포함)으로 서비스에 접근하는 것을 금지하고, 크롤링·스크레이핑은 목적과 관계없이 X의 사전 서면 동의가 없으면 금지한다고 명시한다. 따라서 X는 API로만 조회한다.
- 개발자 정책의 조건 중 SCLS와 관련 있는 것은 다음과 같다.
  - 사용 목적(use case)을 신청 때 서면으로 밝혀야 하고 그 설명이 구속력을 가진다. 크게 벗어나면 위반이다.
  - X 콘텐츠를 저장하면 X에서 삭제·수정된 내용을 따라가야 한다. 삭제 요청이나 원본 삭제가 있으면 가능한 빨리, 늦어도 24시간 안에 반영해야 한다.
  - 게시물을 화면에 보여 줄 때는 API로 최신 내용을 가져와야 하며, API에서 사라진 게시물은 내려야 한다.
  - 제3자(공개 API 포함)에는 게시물 ID만 줄 수 있다. 본문 재배포는 제한된다.
  - 요금제의 범위를 넘는 사용은 Enterprise 계약이 필요하다. 범위의 기준은 정책에 구체적으로 나와 있지 않다.

**Instagram (직접 열람: Meta 개발자 문서 개요, [이용 약관](https://help.instagram.com/581066165581870/?locale=ko_KR)(2025-01-01 시행), Meta 자동 데이터 수집 약관)**
- 대상은 프로페셔널(비즈니스·크리에이터) 계정이다. 앱 사용자가 권한을 준 데이터만 읽는 것이 원칙이다.
- 다른 계정 정보를 읽는 엔드포인트는 Business Discovery와 Hashtag Search 둘이며, Hashtag Search는 Facebook 로그인 방식에서만 되고 허용 용도가 캠페인 탐색·브랜드 감성 분석 등으로 한정된다. 행사 공지 수집은 이 용도 목록에 없다.
- 내가 소유·관리하지 않는 계정을 다루려면 고급 접근(App Review와 비즈니스 인증)이 필요하다.
- 이용 약관 4.2항은 Instagram의 명시적 허가 없이 자동화된 방식으로 정보에 접근하거나 수집하는 행위를, 로그인 여부와 관계없이 금지한다. 접근을 제어하는 기술적 수단을 우회하는 것도 금지한다. API 사용은 별도로 Meta 플랫폼 약관과 개발자 정책을 따른다(7.1항).
- Meta 자동 데이터 수집 약관(2024-10-07 시행)도 Meta의 명시적 서면 허가 없는 자동 수집을 금지하고, 약관에 동의하는 것만으로는 허가가 되지 않는다고 밝힌다. robots.txt 준수 의무가 있고 API 예외 조항은 없다. 이 약관에 Instagram이 직접 지명되어 있지는 않다.
- 따라서 Instagram은 자동 수집 대상에서 빼고 수동 제보·공식 사이트 위주로 조정하는 편이 안전하다. Meta 플랫폼 약관과 개발자 정책은 열람하지 않았다.

**YouTube (직접 열람: Data API v3 문서)**
- 기본 할당은 하루 10,000 단위이고 `search.list`는 별도로 하루 100회이다. `playlistItems.list`·`channels.list`·`videos.list`는 1회에 1단위이다. 증액은 신청서로 요청한다.
- 공식 채널의 업로드 목록을 하루 몇 번 읽는 정도면 기본 할당으로 충분하다. AGF는 전용 채널이 없고 ANIPLUS 채널(`@ANIPLUSINC`)을 쓰므로 AGF와 무관한 영상이 섞인다. 이 채널은 제목·설명의 키워드 필터가 필요하다. 이용약관은 열람하지 않았다.

**그 밖의 채널** (Facebook·TikTok·LINE·카카오톡 채널·Twitch)은 이번에 조사하지 않았다.

### 4. 제안 (결정 전)

- 첫 Collector 후보는 코미케(일정 페이지가 정적이고 경로 규칙이 일정함)와 AGF·PlayX4 공지(`sitemap.xml` 제공)이다.
- 수집기는 식별 가능한 User-Agent와 연락처를 밝히고, robots.txt를 따르고, 요청 간격을 제한한다.
- 일러스타 페스는 X 공지 계정 `@illustar_notice`가 사실상 주 출처이고 공식 사이트는 렌더링 방식 때문에 자동 수집이 어렵다. 이 시리즈는 X API 비용을 감수할지가 수집 여부를 정한다.
- X는 유료 API 비용 상한을 정한 뒤 공식 계정 위주로 쓰고, Instagram은 자동 수집에서 제외하는 방향으로 [05 문서의 리스크 메모](../plan/05-storage-and-collection.md#521-행사별-수집-프로필)대로 범위를 조정한다.
- X를 쓰기로 하면 사용 목적 신청서에 수집 대상(공식 계정 목록)과 용도를 구체적으로 적어야 한다. 또한 [§5.1.1](../plan/05-storage-and-collection.md#511-저장-대상)의 "SNS 원본 JSON 보관"은 X 삭제 반영 의무(24시간)와 맞는지 보관 방식을 정하기 전에 검토한다. 저장하는 건 추출한 행사 정보와 게시물 ID·링크 위주로 하는 안을 생각해 볼 수 있다.
- 지스타는 사무국에 수집 가능 여부를 문의한다(문의 채널은 `biz@soiv-studio.xyz`, 답변 전까지는 수동 등록).
- 원문 HTML 스냅샷 보관([§5.1.1](../plan/05-storage-and-collection.md#511-저장-대상))은 저작권 관점의 검토가 따로 필요하다. 이번 조사는 수집 허용 여부만 다뤘다.

### 미확인과 후속

- X 이용약관·개발자 정책과 Instagram 이용 약관, Meta 자동 데이터 수집 약관은 원문을 읽었다. 단 일반 요청으로는 본문이 읽히지 않아 앱 내 브라우저로 열었다(`help.x.com`은 일반 요청에서 403).
- Meta 플랫폼 약관·개발자 정책, X 자동화 규칙(Automation Rules)과 API 제한 사용 규칙은 열람하지 않았다.
- 약관은 개정될 수 있어 실제 신청 전에 다시 확인한다. 법적 해석은 하지 않았고 문구를 정리한 것이다.
- 각 행사 사이트의 이용약관 본문은 읽지 않았다.
- 사용자가 알려 준 계정과 주소(AGF·WONDERLIVET·일러스타 페스의 SNS, 일러스타 공지 주소)는 직접 접속해 열어 보지 않았다.
- 일러스타 페스와 WONDERLIVET 공식 사이트의 공지 본문은 클라이언트 렌더링이라 열람하지 못했다.
- 후속은 [로드맵 Phase 0](../plan/11-roadmap-and-success.md)의 "초기 수집 출처·이용 조건 확인"에서 관리한다.
