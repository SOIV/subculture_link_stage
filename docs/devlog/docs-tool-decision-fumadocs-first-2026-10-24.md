# Docs 사이트 도구 결정 변경 — Fumadocs 우선, Starlight 차선 (2026-10-24)

개발자 문서 사이트 도구를 "Starlight 확정, Fumadocs 차선"에서 **"Fumadocs 우선, Starlight(+Scalar) 차선"** 으로 바꾼 기록이다. 결정은 사용자가 했고, 이 파일은 그 근거가 된 중요 조건 비중 분석과 착수 시 보완 항목, 차선 전환 신호를 남긴다. Claude(Sonnet 5.5)가 작성했다.

- 단계·성격: Phase 2 사전 결정 / 설계 확정(사용자 결정). 구현은 시작하지 않았다.
- 이전 결정과의 관계: [2026-10 작업 로그](2026-10.md)의 "API Docs 사이트 도구 확정(Starlight)"을 이 기록이 대체한다. 이전 기록은 이력으로 남긴다.
- 표기: **(판단)** 은 작성자의 추정이다. 별도 표시가 없는 사실은 [PoC 실행 결과](docs-tool-poc-results-2026-10-24.md)와 [Codex PoC 결과](docs-site-tools-poc-results-codex-2026-10-24.md)에서 확인한 것이다.
- 한계: **두 구성의 격차는 근소하다.** 강한 추천이 아니라 "통합 경험을 우선한 선택"이다. 실제 Cloudflare 배포와 규모가 커진 뒤의 비용은 검증하지 않았다.

## 1. 결정 내용

| 구분 | 내용 |
|---|---|
| 우선 | **Fumadocs** — Next.js 정적 export(`output: 'export'`) + 공식 `fumadocs-openapi` + MDX 가이드 + `/ko`·`/ja`·`/en` 명시 경로 + 정적 검색 |
| 차선 | **Starlight + Scalar** — `starlight-openapi`는 제외한다(플레이그라운드가 없고 생성 페이지 UI가 영어로 고정돼 있다) |
| 배포 방향 | Cloudflare에 정적 산출물을 올린다. 서버 기능, 미들웨어(`proxy`), OpenNext, 플레이그라운드용 프록시는 쓰지 않는다. 공개 `/v1`이 CORS를 전체 허용하므로 브라우저가 직접 요청한다 |
| OpenAPI 번역 | 언어별 OpenAPI 문서(`ko`·`ja`·`en`)를 두고 언어별로 페이지를 생성하는 방향이다 |

아직 정하지 않은 것은 다음과 같다.

- 문서 사이트 배포 경로와 서브도메인
- 스펙 작성 방식(Spec-first 대 Code-first, [08 §8.5.2](../plan/08-api-and-ics.md#852-미결-사항))
- 언어별 스펙 관리 방식(3개 파일과 구조 검사 스크립트, 또는 OpenAPI Overlay)
- 문서 버전 관리(공개 계약이 `/v1` 하나인 동안은 불필요)
- Phase 2의 비공개 접근 제한 방식
- 미번역 안내와 한국어 검색 보완 방식

## 2. 중요 조건 비중 분석

PoC에서 필수 조건은 두 구성이 모두 통과했다. 아래는 중요 조건 사이의 차이만 본 것이다. **(판단)** 점수와 가중치는 작성자가 정했고, 측정값이 아니다. Codex는 같은 이유로 점수화를 하지 않았다.

### 방법

- 항목별로 SCLS 우선순위에 맞춰 가중치(합 100)를 주고 0~1 점수를 매겼다.
- 100점 만점 점수를 두 구성의 합 100%로 환산했다. 어느 쪽이 더 좋을 확률이 아니라 충족도의 비율이다.

### 결과 (SCLS 현재 우선순위: API 개발자 문서가 주력)

| 항목 | 가중치 | Starlight + Scalar | Fumadocs |
|---|---:|---:|---:|
| 가이드 다국어 | 15 | 0.95 → 14.3 | 0.80 → 12.0 |
| 레퍼런스·플레이그라운드 | 25 | 0.80 → 20.0 | 0.95 → 23.8 |
| 가이드 검색 | 10 | 0.90 → 9.0 | 0.70 → 7.0 |
| 레퍼런스 검색·통합 | 15 | 0.45 → 6.8 | 0.85 → 12.8 |
| 정적 배포 | 10 | 0.85 → 8.5 | 0.85 → 8.5 |
| 스펙 변경 갱신 | 10 | 0.90 → 9.0 | 0.80 → 8.0 |
| 유지보수 부담 | 15 | 0.60 → 9.0 | 0.60 → 9.0 |
| **합계(100점 만점)** | 100 | **76.5** | **81.0** |
| **합 100%로 환산** | | **약 49%** | **약 51%** |

### 점수를 매긴 이유

| 항목 | 이유 |
|---|---|
| 가이드 다국어 | Starlight는 설정만으로 되고 한·일 UI 문자열 31/31이 내장돼 있으며 미번역 안내가 기본이다. Fumadocs는 `[lang]` 라우트를 직접 구성하고, 공식 언어 팩이 중국어뿐이라 UI 사전 63개를 직접 써야 하며, 미번역 안내는 직접 구현해야 한다(Codex가 작은 구현으로 가능함을 확인했다) |
| 레퍼런스·플레이그라운드 | 둘 다 JSON·400·429·ICS 실요청이 통과했다. Fumadocs는 사전 210개(UI 63 + OpenAPI 151)를 모두 번역하자 기술 표기를 빼고 영어가 남지 않았고 모달 겹침도 없었다. Starlight는 Scalar UI 번역 키 약 517개 중 103개만 번역했을 때 영어가 여러 곳 남았고, Starlight 사이드바를 유지하면 모달이 사이드바에 가려졌다(`splash` 템플릿으로 피할 수 있다) |
| 가이드 검색 | Pagefind는 한국어 조사 변형("구독을", "티켓을")을 찾았고 Fumadocs는 못 찾았다. 반대로 한국어 화면의 `v1`, `/v1/events`는 Pagefind가 0건이었고 Fumadocs는 찾았다 |
| 레퍼런스 검색·통합 | Fumadocs는 가이드와 레퍼런스가 같은 검색에 나온다. Starlight는 Pagefind가 레퍼런스를 색인하지 못해 Scalar 자체 검색을 따로 써야 한다. 파라미터·응답 필드 설명까지의 색인은 양쪽 모두 부족했다 |
| 정적 배포 | 비긴다. Starlight는 산출물이 1.36MB로 가볍지만 Scalar 번들 4.86MB(전송 1.32MB)를 CDN에서 받거나 자체 호스팅해야 한다. Fumadocs는 외부 요청이 0건이고 산출물이 17.7MB다. 둘 다 루트 `/` 처리가 필요하다 |
| 스펙 변경 갱신 | Starlight는 스펙을 복사하고 빌드하면 된다. Fumadocs는 MDX 생성 단계가 하나 더 있다 |
| 유지보수 부담 | 장단이 상쇄돼 같게 줬다. Starlight는 벤더가 둘이고 이음매를 관리해야 한다. Fumadocs는 Next 16, React 19의 빠른 릴리스, 패키지 459개, 한 번 난 빌드 실패가 부담이다 |

### 가중치를 바꾸면

| 시나리오 | 가중치(가이드 다국어 / 레퍼런스 / 가이드 검색 / 레퍼런스 검색 / 정적 / 갱신 / 유지보수) | Starlight + Scalar | Fumadocs | 환산 |
|---|---|---:|---:|---|
| SCLS 현재 우선순위 | 15 / 25 / 10 / 15 / 10 / 10 / 15 | 76.5 | 81.0 | 49 : 51 |
| 가이드 중심 | 25 / 10 / 15 / 5 / 10 / 10 / 25 | 80.0 | 75.8 | 51 : 49 |
| 레퍼런스·검색 통합 중시 | 10 / 30 / 5 / 25 / 10 / 5 / 15 | 71.3 | 82.8 | 46 : 54 |

어느 시나리오에서도 격차는 4~11점이다. 가이드 중심이면 Starlight가 근소하게 앞서고, 레퍼런스·검색 통합을 중시하면 Fumadocs가 앞선다. 점수만으로 결정할 수준이 아니라서, 아래 이유로 우선순위를 정했다.

## 3. 이 선택의 이유

- SCLS 문서는 **API 개발자 문서가 주력**이고 그 핵심은 레퍼런스와 플레이그라운드다. 이 부분에서 Fumadocs는 가이드와 같은 사이드바·검색·언어 전환을 쓰고 외부 CDN이 없다.
- 두 구성 모두 정적 다국어 API 문서를 만들 수 있다는 사실은 두 PoC에서 확인됐다. 남은 차이는 "검색과 탐색을 얼마나 통합할 것인가"이고, 이 프로젝트는 통합 쪽을 택했다.
- Starlight의 장점(가이드 다국어 설정, 미번역 안내, 한국어 조사 검색, 가벼운 가이드 페이지)은 차선으로 보존한다.

## 4. 착수 시 보완할 항목

Fumadocs 쪽 약점은 기본 제공이 아니어서 직접 메워야 한다. 구현 착수 때 다음을 처리한다.

- [ ] **미번역 안내.** 대체 본문만 나오므로 안내 컴포넌트를 구현한다. Codex PoC(`poc/docs-frameworks/apps/fumadocs`)에 작은 구현 예가 있다.
- [ ] **한국어 조사 변형 검색.** 기본 검색은 어절 그대로 비교해 "구독을"이 "구독"을 찾지 못한다. 품질을 평가하고 보완 방법(다른 검색 엔진, 토크나이저)을 검토한다. 이 보완책은 아직 조사하지 않았다.
- [ ] **한·일 UI 번역 사전 210개.** 작성, 원어민 검수, 패키지 업데이트 때 키 추가·변경 추적.
- [ ] **정적 export 제약.** `proxy`, redirects, rewrites, headers를 쓸 수 없고 Route Handler는 정적 GET만 된다. 루트 `/` 리다이렉트(`public/index.html` meta refresh 등), 로고 링크가 현재 언어를 유지하도록 `nav.url` 설정, 본문 링크는 상대 파일 링크 사용.
- [ ] **언어별 스펙 관리.** 3개 파일과 구조 검사 스크립트(CI), 또는 OpenAPI Overlay. 스펙을 바꾸면 `generateFiles`를 로케일별로 다시 실행한다. 구현된 계약만 반영한다(페이지네이션 없음, `locale`은 `ko|ja|en`, `ko-KR`은 `ko`로 처리).
- [ ] **버전 고정과 업그레이드 주기.** `fumadocs-core`·`fumadocs-ui` 16.x, `fumadocs-openapi` 12.x, `next` 16.x, `react` 19.x가 일 단위로 릴리스된다. 한 번 난 빌드 실패(Windows `esbuild spawn UNKNOWN`)의 원인은 모른다.
- [ ] **산출물 크기.** 17.7MB, 493파일이다. Cloudflare 정적 자산의 파일 수·크기 제한은 확인하지 않았다.
- [ ] **Phase 2 비공개 접근 제한.** 문서 소스는 공개 저장소에 있으므로 사이트 접근 제한만으로는 비공개가 되지 않는다. 비공개 초안의 소스 보관 범위를 구분한다.
- [ ] **검색 범위.** 파라미터·응답 필드 설명까지 검색해야 한다면 추가 색인 설계가 필요하다(양쪽 공통).

## 5. Starlight 차선으로 전환하는 신호

- 우선순위가 가이드 중심으로 바뀌고 API 레퍼런스를 작게 유지하기로 할 때
- 한국어 조사 변형 검색이 중요하다고 판명되고 Fumadocs에서 보완하기 어려울 때
- Fumadocs의 업그레이드·빌드 부담이 1인 운영에 과하다고 확인될 때

차선 구성은 **Starlight + Scalar** 이며 다음을 따른다.

- Scalar는 고정 버전 번들을 패키지에서 복사해 자체 호스팅한다(기본 CDN은 버전이 고정되지 않는다).
- API 화면은 `splash` 템플릿이나 `layout: 'classic'` 중 하나를 골라 이중 사이드바와 모달 겹침을 피한다. 배치에 따라 Scalar 검색 표시 여부가 달라진다([PoC 결과 12절](docs-tool-poc-results-2026-10-24.md#12-codex-poc와의-대조와-정정)).
- Scalar 한·일 UI 문구는 영어 대체를 허용하며 점진적으로 번역한다.
- **전환 비용을 줄이려면** 가이드 본문은 일반 마크다운 위주로 쓰고 도구 전용 컴포넌트와 자체 플러그인을 최소화한다. OpenAPI 스펙은 도구와 독립이라 그대로 쓸 수 있다.
