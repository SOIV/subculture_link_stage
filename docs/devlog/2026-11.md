- 정한 것(사용자 결정): 자동 제안보다 검수함과 제안 틀을 먼저 만든다(지금 쌓인 AGF 38건은 대부분 2025년 지난 공지라 자동 제안으로 나올 것이 적음). 처음 다루는 제안은 일정 추가·수정.

## 2026-11-19 — Onstage 계정 범위와 로그인 수단 정리

- 단계·성격: 계획 정리(코드 변경 없음)
- 정한 것(사용자 결정):
  - Onstage 일반 사용자 로그인은 지금 만들지 않는다. 지금 기능(보기·검색·캘린더 구독)은 로그인이 필요 없고, 계획대로 Phase 4(제안 기능)에서 만든다.
  - 로그인을 쓰는 곳은 Phase 4 제안 기능, Phase 6 개인 캘린더 주소, Phase 6 개발자 콘솔이다. 캘린더 주소와 API 키는 둘 다 "계정마다 발급하는 비밀 값"이라 Onstage "내 계정" 페이지 하나에서 관리한다. 다른 점은 캘린더 주소는 다시 보여 줄 수 있게 저장하고, API 키는 한 번만 보여 주고 해시만 저장하는 것([08 §8.5.1](../plan/08-api-and-ics.md#851-단계별-계획), [§8.6.5](../plan/08-api-and-ics.md#865-피드-품질)).
  - 개발자 콘솔은 Backstage에 넣지 않는다(관리 화면의 출입구를 외부 개발자에게 넓히지 않기 위해). 문서 사이트도 정적 사이트로 유지하고 콘솔로 링크만 한다.
  - 로그인 수단은 처음에는 Google·LINE 두 가지. Google은 기본, LINE은 일본 점유율 때문이고 둘 다 무료다. Apple은 일본 아이폰 사용자에게 유용하지만 매년 연회비가 들어, 원하는 사용자가 생기면 그때 검토한다(웹 서비스라 의무는 아님). 제외: X(로그인에도 유료 API 호출, 이메일 기본 제공 안 함), 카카오(지원 안 함), GitHub(일반 팬에게 낯섦), Discord(로그인으로는 잘 안 쓸 것으로 봄).
  - 이메일 인증 코드 로그인은 처음에는 두지 않는다. Google Workspace로 보내는 안도 있었지만 발송 평판·스팸 처리·발송 한도 등 운영 부담이 커서, 소셜 로그인만으로 시작한다(비밀번호·메일 발송 없음).
- 참고(Apple 로그인 준비물, 구현 때 다시 확인): Apple Developer Program 가입(1회성이 아니라 매년 내는 연회비, 미국 기준 99달러), Services ID와 도메인 등록, 비밀 키(.p8)로 만드는 client secret을 최대 6개월마다 새로 만들어야 함, 이름은 첫 로그인 때 한 번만 옴, "이메일 가리기"를 고른 사용자는 Apple 중계 주소가 와서 메일을 보내려면 보내는 도메인을 Apple에 등록해야 함.
- 문서 사이트 Cloudflare 배포·Access 잠금은 2026-11-18 사용자가 배포와 함께 설정함(로드맵 체크).

## 2026-11-18 — 수집기 착수: 코미케·AGF 수집 → 저장 → Backstage에서 보기

- 단계·성격: Phase 2 / 공식 웹사이트 Collector 첫 단계([로드맵](../plan/11-roadmap-and-success.md), [05 §5.3.1](../plan/05-storage-and-collection.md#531-기본-흐름))
- 정한 것(사용자 결정): 첫 출처는 코미케 일반 참가 안내(일본어)와 AGF Korea 공지(한국어). 이번 범위는 수집 → 저장 → Backstage에서 보기까지이고, 변경 제안(검수 대기열)은 다음 단계.
- 확인한 것: 두 사이트 모두 robots.txt가 해당 주소를 막지 않는다(코미케는 `/staff/`만, AGF는 `/exclude`만). 코미케 사이트에는 이용약관이 없고 "링크하실 분께" 안내만 있다(링크는 첫 화면 주소를 써 달라는 내용, 수집 제한 문구는 없음). AGF 사이트는 이용약관 링크가 없다. AGF 공지 화면은 스크립트로 목록을 채워 HTML에 글이 없어서, 화면이 부르는 목록 주소(JSON)를 읽기로 했다.
- 변경(Private `scls-platform`):
  - DB: `collection_jobs`(수집 작업 기록), `collected_documents`(수집 문서) 추가. migration `20261118090000_add_collection_jobs_and_documents` — 운영 DB에는 아직 적용 안 함. 참고 DDL보다 `collected_documents.collection_job_id`(처음 저장한 작업)를 하나 더 둠.
  - API: 수집기 전용 `/worker/*`(출처 목록, 작업 시작, 문서 보내기, 작업 끝내기), `WORKER_API_TOKEN` 인증. 비활성 출처는 작업을 시작할 수 없다. 중복(제목+본문 해시)·리비전 규칙은 API 한 곳에. Backstage용 읽기 경로(수집 작업 목록, 수집 문서 목록·본문).
  - 수집기(`apps/worker`, Python): `httpx`+`selectolax`, robots.txt 확인·3초 간격·저장소 주소가 든 User-Agent. 수집 방법 두 가지(페이지 통째로 받기 / AGF 게시판). `try` 명령으로 API 없이 결과 확인.
  - Backstage: 수집 출처 표에 "수집 기록" 버튼 → 최근 수집 작업과 수집 문서(리비전·언어·본문 보기). 수집 문서가 있는 출처는 지울 수 없어서 안내 문구를 띄운다(끄기로 대신).
- 확인: API 테스트 249개(새로 13개), 수집기 테스트 10개, 타입 검사·Backstage 빌드·OpenAPI 스펙 확인 통과. `try`로 실제 두 사이트를 한 번씩 읽어 코미케 1건(일본어, 표 칸 구분 포함)·AGF 10건(한국어, 등록일 한국 시각)을 확인했다. migration을 적용하지 않아 API로 저장하는 것과 Backstage 화면은 아직 실제로 보지 못했다.
- 후속: migration 적용 → 두 출처 활성화 → 첫 수집(`--backfill`)과 화면 확인(사용자), 정기 실행 위치·Queue, 원본 HTML 보관(Storage Object), 변경 제안 생성.
- 첫 수집(2026-11-19, 사용자 실행): migration 적용 후 두 출처를 켜고 `run --force --backfill` — 코미케 1건, AGF 공지 38건(게시판 전체 글 수와 같음) 저장, 두 작업 모두 성공. 같은 날 사용자 요청으로 Backstage 수집 출처 목록을 활성 출처가 먼저 오게 바꿈(그 안에서는 우선순위·등록 순).

## 2026-11-18 — OpenAPI 스펙에 요청 수 제한(429)·응답 헤더 추가, 429가 500으로 나가던 문제 수정

- 단계·성격: Phase 2 / OpenAPI 스펙 보완([08 §8.5.2](../plan/08-api-and-ics.md#852-미결-사항)), 공개 API 오류 수정
- 발견: 공개 `/v1`의 요청 수 제한(방문자 IP당 분당 600회)에 걸리면 429가 아니라 500(`FST_ERR_RESPONSE_SERIALIZATION`)이 나가고 있었다. 2026-11-17 응답 직렬화를 Zod 스키마로 바꾸면서 생긴 문제로, 제한 플러그인이 던진 값에 상태 코드가 정해지지 않아 200 응답 스키마로 직렬화하려다 실패했다. 기존 제한 테스트는 공개 라우트 없이 따로 만든 앱으로 돌아서 이를 잡지 못했다. 정상 사용에서는 한도에 닿지 않아 화면에 드러난 적은 없다.
- 변경(Private `scls-platform`):
  - `public-api.ts`: 공개 범위의 오류 처리에서 요청 수 제한을 직접 429 `{ success: false, error: "RATE_LIMITED", retryAfterSeconds }`로 돌려준다. 모든 공개 라우트의 응답 스키마에 429(`RateLimitedResponse`)를 자동으로 붙여 실제 응답과 스펙이 같은 정의를 쓴다.
  - `scripts/generate-openapi.ts`: 모든 응답에 `X-RateLimit-Limit`·`X-RateLimit-Remaining`·`X-RateLimit-Reset`, 429에 `Retry-After`, 200에 `Cache-Control`을 적는다. `Cache-Control` 값은 `lib/public-hardening.ts`의 상수를 그대로 가져온다(JSON `public, max-age=60, stale-while-revalidate=300`, ICS `public, max-age=300`, health `no-store`).
- 확인: 새 테스트 4개(실제 공개 라우트에서 한도 초과 시 429·본문·`Retry-After`, 캘린더 피드도 429, 성공 응답의 제한 헤더·`Cache-Control`, 스펙의 모든 작업에 429·헤더가 적혔는지). 전체 229개 통과, 타입 검사·빌드 통과.
- 후속: 푸시하면 Fly가 자동 배포한다. 스펙에 남은 것은 언어별 설명 문구 방식과 Fumadocs 문서 사이트.

## 2026-11-17 — Onstage 행사 상세에 네이버 지도·카카오맵 링크 추가

- 단계·성격: Phase 1 / Onstage 상세 페이지 개선
- 변경: 장소 칸의 "지도에서 보기"가 구글 지도 하나뿐이던 것을, 한국 행사(`countryCode = KR`)는 네이버 지도 · 카카오맵 · 구글 지도 버튼 3개로 바꿨다. 해외 행사는 지금처럼 구글 지도 하나만 둔다(`apps/onstage/src/lib/map.ts`, 3개 언어 이름 추가).

## 2026-11-05 — 수집 Worker 구현 언어를 Python으로 정함

- 단계·성격: Phase 2 사전 결정 / 설계 방향 확정(라이브러리·Queue는 착수 때 확정)
- 변경: 아직 만들지 않은 수집 Worker(`scls-worker`)를 Python으로 만들기로 했다. 이미 있는 API·Backstage·Onstage는 TypeScript 그대로 둔다.
- 이유:
  - JS/TS 외의 언어도 함께 써 보려는 목적이 있었고, 그중 효과가 가장 큰 곳을 골랐다.
  - 수집 흐름([§5.3.1](../plan/05-storage-and-collection.md#531-기본-흐름))에는 크롤링, 일본어·한국어 날짜 읽기, 텍스트 분류·임베딩처럼 Python 라이브러리가 더 많은 일이 몰려 있다.
  - 이미 있는 코드는 바꾸지 않는다. API·Backstage는 `packages/db`·`packages/domain`의 타입을 같이 쓰고 있어 한쪽만 바꾸면 공유가 끊긴다. Backstage·Onstage는 브라우저와 Cloudflare Workers에서 돌아가므로 JS/TS여야 한다. seed 스크립트는 Prisma를 쓰므로 TS가 편하다.
  - Go·Rust 등은 지금 규모에서 속도가 문제 되는 곳이 없어 넣지 않는다.
- 정한 규칙:
  - Python Worker는 DB에 직접 쓰지 않고 API의 Worker 전용 경로를 거친다. Prisma 타입을 Python에서 쓸 수 없으므로 DB 규칙을 TS API 한 곳에만 두기 위해서다 ([§3.2.1](../plan/03-architecture-and-domain.md#321-repository-구조-확정)).
  - 원본 HTML·이미지는 Worker가 R2에 바로 올리고 메타데이터만 API로 보낸다.
  - Queue는 Python에서도 쓸 수 있어야 한다. pg-boss는 Node 전용이라 빠지고, BullMQ는 Python 패키지의 기능 범위를 확인해야 한다. Postgres 표 기반 직접 구현이 가장 단순한 후보다 ([§10.1.2 미결 사항](../plan/10-infra-ops-security.md#1012-배포-구조-예시)).
- 관련: [03 §3.2.1](../plan/03-architecture-and-domain.md#321-repository-구조-확정), [05 §5.3.1](../plan/05-storage-and-collection.md#531-기본-흐름), [10 §10.1.1·§10.1.2](../plan/10-infra-ops-security.md#1011-권장-기술-스택), [로드맵 Phase 2](../plan/11-roadmap-and-success.md)
- 확인: 문서 결정만 했다. Python 코드·라이브러리는 아직 설치하거나 시험하지 않았다. BullMQ Python 패키지의 기능 범위도 직접 확인하지 않았다.
- 후속: Worker와 API가 주고받을 데이터 정의 방식(OpenAPI 또는 JSON Schema), Queue 선택, 번역·알림 생성을 Python에 둘지 여부. 로드맵 Phase 2의 "공식 웹사이트 1~2개 Collector 구현"에서 관리한다.
