# 2026-11 작업 로그

## 2026-11-05 — 수집 Worker 구현 언어를 Python으로 정함

- 단계·성격: Phase 2 사전 결정 / 설계 방향 확정(라이브러리·Queue는 착수 때 확정)
- 변경: 아직 만들지 않은 수집 Worker(`scls-worker`)를 Python으로 만들기로 했다. 이미 있는 API·Backstage·Onstage는 TypeScript 그대로 둔다.
- 이유:
  - JS/TS 외의 언어도 함께 써 보려는 목적이 있었고, 그중 효과가 가장 큰 곳을 골랐다.
  - 수집 흐름([§5.3.1](../plan/05-storage-and-collection.md#531-기본-흐름))에는 크롤링, 일본어·한국어 날짜 읽기, 텍스트 분류·임베딩처럼 Python 라이브러리가 더 많은 일이 몰려 있다.
  - 이미 있는 코드는 바꾸지 않는다. API·Backstage는 `packages/db`·`packages/domain`의 타입을 같이 쓰고 있어 한쪽만 바꾸면 공유가 끊긴다. Backstage·Onstage는 브라우저와 Cloudflare Workers에서 돌아가므로 JS/TS여야 한다. seed 스크립트는 Prisma를 쓰므로 TS가 편하다.
  - Go·Rust 등은 지금 규모에서 속도가 문제 되는 곳이 없어 넣지 않는다.
- 정한 규칙:
  - Python Worker는 DB에 직접 쓰지 않고 API의 Worker 전용 경로를 거친다. Prisma 타입을 Python에서 쓸 수 없으므로 DB 규칙을 TS API 한 곳에만 두기 위해서다 ([§3.2.1](../plan/03-architecture-and-domain.md#321-repository-구조-확정)).
  - 원본 HTML·이미지는 Worker가 R2에 바로 올리고 메타데이터만 API로 보낸다.
  - Queue는 Python에서도 쓸 수 있어야 한다. pg-boss는 Node 전용이라 빠지고, BullMQ는 Python 패키지의 기능 범위를 확인해야 한다. Postgres 표 기반 직접 구현이 가장 단순한 후보다 ([§10.1.2 미결 사항](../plan/10-infra-ops-security.md#1012-배포-구조-예시)).
- 관련: [03 §3.2.1](../plan/03-architecture-and-domain.md#321-repository-구조-확정), [05 §5.3.1](../plan/05-storage-and-collection.md#531-기본-흐름), [10 §10.1.1·§10.1.2](../plan/10-infra-ops-security.md#1011-권장-기술-스택), [로드맵 Phase 2](../plan/11-roadmap-and-success.md)
- 확인: 문서 결정만 했다. Python 코드·라이브러리는 아직 설치하거나 시험하지 않았다. BullMQ Python 패키지의 기능 범위도 직접 확인하지 않았다.
- 후속: Worker와 API가 주고받을 데이터 정의 방식(OpenAPI 또는 JSON Schema), Queue 선택, 번역·알림 생성을 Python에 둘지 여부. 로드맵 Phase 2의 "공식 웹사이트 1~2개 Collector 구현"에서 관리한다.
