# 2026-11 작업 로그

## 2026-11-17 — 티켓 구조 재검토와 끝난 판매 자동 "종료" 표시

- 단계·성격: Phase 1 / 티켓 판매 구조 재검토(Onstage 리디자인 뒤로 미뤄 둔 항목)
- 점검: DB 표, 공개 API 응답, Onstage 상세 화면, 공개 행사 7곳의 실제 데이터를 맞대어 봤다. 표 구조는 충분해서 마이그레이션 없이 필수·선택·보류·안 함을 정리했다([04 DB 설계](../plan/04-database-design.md)).
- 찾은 문제:
  - 판매가 끝나도 상태가 "확정"으로 남았다. WONDERLIVET "일반 발매 · 티켓피아"는 11/9에 끝났는데 확정이었다. 상세 화면은 일정 상태를 아예 보여 주지 않았다.
  - `TICKET_OPEN`의 `COMPLETED`가 "시작됨"의 뜻으로도 쓰였다. WONDERLIVET 국내 판매와 AGF 일반 판매는 아직 판매 중일 텐데 DB에 `COMPLETED`로 들어가 있다.
  - AGF 판매 일정은 하루짜리 종일 일정(시작일만)이고, WONDERLIVET 티켓피아는 시작~마감 기간이라 `ends_at`의 뜻이 섞여 있었다.
  - 티켓 정보가 없는 행사 4곳, 예매처 링크가 빈 곳(AGF·지스타 — 사용자가 Backstage로 채움).
- 변경:
  - Private `scls-platform`: 공개 API가 끝 시각이 지난 예정·확정 일정을 `COMPLETED`로, 끝난 확정 행사를 `ENDED`로 내보낸다(`lib/derived-status.ts`, 응답에서만 계산하고 DB는 그대로). 마감 없는 판매는 행사 끝까지, 하루짜리 종일 판매 시작은 시작일로 본다(캘린더 피드와 같은 기준).
  - Onstage 상세 화면: 끝난·취소된 일정은 흐리게 하고 "종료"·"취소" 표시, 연기는 흐리지 않고 "연기" 표시(3개 언어).
  - 상태와 기간의 뜻을 [04 DB 설계](../plan/04-database-design.md)에 적었다.
- 확인: API 단위 테스트 214개 통과(새 상태 계산 10개 포함), 타입 검사 통과, `svelte-check` 오류 0. 로컬 API(운영 DB 읽기)와 로컬 Onstage로 WONDERLIVET 상세(라이트·한국어)와 코믹월드 337 상세(다크·일본어, 행사 "終了")를 화면으로 확인했다.
- 후속: DB에 `COMPLETED`로 잘못 들어간 판매 중 일정 정리, 비어 있는 티켓 정보 채우기(로드맵 Phase 1).

## 2026-11-17 — 초기 수집 출처 32건을 운영 DB에 입력

- 단계·성격: Phase 2 / Sources 데이터 반영
- 변경: 2026-10-21에 준비한 초기 9개 시리즈 출처 32건을 `seed:sources --apply`로 운영 DB에 넣었다. 전부 비활성이라 수집기가 생겨도 켜기 전까지는 아무것도 가져가지 않는다.
- 막혔던 것과 해결:
  - Sources migration(`20261021090000_add_sources`)은 이미 운영 DB에 적용되어 있었다(`prisma migrate status` 확인).
  - 입력 스크립트가 "DB에 없는 시리즈"로 멈췄다. Backstage에서 시리즈 슬러그를 바꾼 것이 입력 데이터에 반영되지 않았기 때문이다(`animejapan`→`anime-japan`, `comiket`→`comic-market`). 도쿄 게임쇼는 `tokyo-game show`처럼 띄어쓰기가 들어가 있어 Backstage에서 `tokyo-game-show`로 고쳤다.
  - Private `scls-platform`의 입력 데이터(`seed-data/events-2026.ts`, `sources-2026.ts`)의 시리즈 슬러그를 DB에 맞췄다. 행사 슬러그(`comiket-109` 등)는 바뀌지 않았다.
  - 로컬 Prisma 클라이언트가 Sources 추가 전에 생성된 것이라 `prisma.source`가 없었다. `pnpm --filter @scls/db generate`로 다시 만들었다.
- 관련: [로드맵 Phase 2](../plan/11-roadmap-and-success.md), [출처 조사 기록](2026-10.md)
- 확인: 입력은 사용자가 실행했고 오류 없이 끝났다. 입력된 행 수는 DB에서 직접 세어 보지 않았다.
- 후속: Source Rules, 수집기 구현 때 켤 출처 고르기(지스타 공지 게시판·Instagram은 켜지 않는다).

## 2026-11-10 — OpenAPI 스펙을 코드에서 자동으로 만들기로 정함

- 단계·성격: Phase 2 사전 결정 / [08 §8.5.2](../plan/08-api-and-ics.md#852-미결-사항) 미결 사항 정리(생성 도구는 착수 때 확정)
- 변경: 공개 API 설명서(OpenAPI 스펙)를 사람이 손으로 쓰지 않고, 공개 `/v1` 라우트에 적은 요청·응답 스키마에서 자동으로 뽑기로 했다(Code-first).
- 이유:
  - 1인 운영에서 코드와 설명서를 따로 고치면 둘이 어긋나기 쉽고, 손으로 쓰는 수고도 크다.
  - Fastify는 응답 스키마가 있으면 거기 없는 항목을 응답에서 빼고 보낸다. 내부용 필드가 공개 API로 새는 것을 막는 효과도 있다.
- 참고: 공개 API 자체는 이미 열려 있다(`/v1`, 로그인 없음, 읽기 전용 CORS 전체 허용, IP당 분당 600회 제한). 오픈 API로 쓰기 위해 새로 할 일은 설명서와 문서 사이트이고, API Key는 Phase 6의 한도 상향·Webhook용이다.
- 관련: [08 §8.5.1·§8.5.2](../plan/08-api-and-ics.md#851-단계별-계획), [로드맵 Phase 2](../plan/11-roadmap-and-success.md)
- 확인: 문서 결정만 했다. Private `scls-platform`의 `apps/api/src/server.ts`, `lib/public-hardening.ts`를 읽어 현재 공개 상태를 확인했다. 공개 라우트에는 응답 스키마가 아직 없다. 코드는 바꾸지 않았다.
- 후속: Phase 2 "OpenAPI 3.x 스펙 작성 착수"에서 공개 라우트에 스키마 추가, 생성 도구 선택, 스펙·실제 응답 일치 테스트, 언어별 설명 문구 관리 방식을 정한다.

## 2026-11-05 — 수집 Worker 구현 언어를 Python으로 정함

- 단계·성격: Phase 2 사전 결정 / 설계 방향 확정(라이브러리·Queue는 착수 때 확정)
- 변경: 아직 만들지 않은 수집 Worker(`scls-worker`)를 Python으로 만들기로 했다. 이미 있는 API·Backstage·Onstage는 TypeScript 그대로 둔다.
- 이유:
  - JS/TS 외의 언어도 함께 써 보려는 목적이 있었고, 그중 효과가 가장 큰 곳을 골랐다.
  - 수집 흐름([§5.3.1](../plan/05-storage-and-collection.md#531-기본-흐름))에는 크롤링, 일본어·한국어 날짜 읽기, 텍스트 분류·임베딩처럼 Python 라이브러리가 더 많은 일이 몰려 있다.
  - 이미 있는 코드는 바꾸지 않는다. API·Backstage는 `packages/db`·`packages/domain`의 타입을 같이 쓰고 있어 한쪽만 바꾸면 공유가 끊긴다. Backstage·Onstage는 브라우저와 Cloudflare Workers에서 돌아가므로 JS/TS여야 한다. seed 스크립트는 Prisma를 쓰므로 TS가 편하다.
  - Go·Rust 등은 지금 규모에서 속도가 문제 되는 곳이 없어 넣지 않는다.
- 정한 규칙:
  - Python Worker는 DB에 직접 쓰지 않고 API의 Worker 전용 경로를 거친다. Prisma 타입을 Python에서 쓸 수 없으므로 DB 규칙을 TS API 한 곳에만 두기 위해서다 ([§3.2.1](../plan/03-architecture-and-domain.md#321-repository-구조-확정)).
  - 원본 HTML·이미지는 Worker가 R2에 바로 올리고 메타데이터만 API로 보낸다.
  - Queue는 Python에서도 쓸 수 있어야 한다. pg-boss는 Node 전용이라 빠지고, BullMQ는 Python 패키지의 기능 범위를 확인해야 한다. Postgres 표 기반 직접 구현이 가장 단순한 후보다 ([§10.1.2 미결 사항](../plan/10-infra-ops-security.md#1012-배포-구조-예시)).
- 관련: [03 §3.2.1](../plan/03-architecture-and-domain.md#321-repository-구조-확정), [05 §5.3.1](../plan/05-storage-and-collection.md#531-기본-흐름), [10 §10.1.1·§10.1.2](../plan/10-infra-ops-security.md#1011-권장-기술-스택), [로드맵 Phase 2](../plan/11-roadmap-and-success.md)
- 확인: 문서 결정만 했다. Python 코드·라이브러리는 아직 설치하거나 시험하지 않았다. BullMQ Python 패키지의 기능 범위도 직접 확인하지 않았다.
- 후속: Worker와 API가 주고받을 데이터 정의 방식(OpenAPI 또는 JSON Schema), Queue 선택, 번역·알림 생성을 Python에 둘지 여부. 로드맵 Phase 2의 "공식 웹사이트 1~2개 Collector 구현"에서 관리한다.
